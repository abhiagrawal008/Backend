## Part A — Concepts

### Q1. What is `jsonb` and how is it different from `json`?

Both types store JSON documents in a column. They differ in how the data is stored.

**`json` stores the input text exactly as typed.** Whitespace, key order and duplicate keys are kept. Every time a query reads a key, PostgreSQL must parse the whole text again.

**`jsonb` stores a decomposed binary format.** On insert, the text is parsed once and converted to a binary tree. Whitespace is removed, keys are sorted, and if a key appears twice only the last value is kept.

Effect on speed:

| | `json` | `jsonb` |
|---|---|---|
| Storage | Plain text, an exact copy | Binary, parsed once |
| Write speed | Slightly faster, because it is not converted | Slightly slower, because of the conversion on insert |
| Read/query speed | Slow, because the text is re-parsed on each access | Fast, because keys are reached directly |
| Indexing | No GIN index support | Supports GIN indexes and containment operators (`@>`, `?`) |
| Key order / duplicates | Preserved | Not preserved |

```sql
SELECT '{"b": 1, "a": 2, "a": 3}'::json;   -- {"b": 1, "a": 2, "a": 3}
SELECT '{"b": 1, "a": 2, "a": 3}'::jsonb;  -- {"a": 3, "b": 1}
```

The `jsonb` result shows the keys sorted and the duplicate removed. Because most applications read data far more often than they write it, `jsonb` is the right choice almost every time. `json` is useful only when the exact original text must be kept, for example to store a request log as it was received.

### Q2. How can PostgreSQL be SQL + NoSQL in the same table?

One table can mix ordinary typed columns with a `jsonb` column.

The **typed columns** hold fields that every row has: `id`, `name`, `category`, `price`. They get full relational guarantees: data types, `NOT NULL`, `CHECK`, primary and foreign keys, and joins.

The **`jsonb` column** holds fields that differ from row to row. It behaves like a MongoDB document, with no fixed schema. In a product catalog, a book needs `author` and `pages`, a laptop needs `ram_gb` and `cpu`, and an accessory needs `color` and `wireless`. With only typed columns, we would need many mostly-NULL columns or a separate table for every category.

```sql
CREATE TABLE products (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- SQL part
    name VARCHAR(100) NOT NULL,                             -- SQL part
    category VARCHAR(50) NOT NULL,                          -- SQL part
    price NUMERIC(10,2) NOT NULL,                           -- SQL part
    attributes JSONB                                        -- NoSQL part
);

INSERT INTO products (name, category, price, attributes) VALUES
('Clean Code',     'book',   499.00,    '{"author": "Robert C. Martin", "pages": 464}'),
('MacBook Air M3', 'laptop', 114900.00, '{"ram_gb": 16, "cpu": "Apple M3"}');
```

One query can use both parts:

```sql
SELECT name, price FROM products
WHERE price < 1000 AND attributes ? 'author';
```

Here `price < 1000` is a normal SQL filter and `? 'author'` is a document filter. Adding a new attribute such as `isbn` needs no `ALTER TABLE`, and we keep transactions, joins and constraints on the core columns.

### Q3. The operators `->`, `->>`, `@>` and `?`

The results below are from the `products` table in Part B. They are copied from [output/postgres_output.txt](output/postgres_output.txt).

| Operator | Meaning | Example | Returns |
|---|---|---|---|
| `->` | Get a key's value **as `jsonb`** | `attributes -> 'pages'` (Clean Code) | `464` (type `jsonb`) |
| `->>` | Get a key's value **as `text`** | `attributes ->> 'pages'` (Clean Code) | `464` (type `text`) |
| `@>` | Does the left document **contain** the right one? | `WHERE attributes @> '{"cpu": "Apple M3"}'` | `MacBook Air M3` |
| `?` | Does this **top-level key exist**? | `WHERE attributes ? 'author'` | `Clean Code` |

```sql
SELECT attributes -> 'pages'  AS pages_jsonb, pg_typeof(attributes -> 'pages'),
       attributes ->> 'pages' AS pages_text,  pg_typeof(attributes ->> 'pages')
FROM products WHERE name = 'Clean Code';
--  pages_jsonb | jsonb | pages_text | text
--  464         | jsonb | 464        | text
```

**`->` vs `->>`:** the value looks the same on screen, but the type is different.

- `->` returns `jsonb`. Use it to keep going down a nested document (`attributes -> 'specs' -> 'gpu'`) or to compare against JSON values. A string comes back with its quotes, for example `"Apple M3"`.
- `->>` returns plain `text` without quotes. Use it in `WHERE`, `ORDER BY` or in casts: `(attributes ->> 'ram_gb')::int >= 16`. A JSON number can't be compared directly with an SQL integer, so you must take the text with `->>` and cast it.

### Q4. How does a GIN index on `jsonb` change performance?

A GIN (Generalized Inverted Index) works like the index at the back of a book. It splits every document into its keys and key/value pairs and stores, for each one, the list of rows that contain it. To find `{"wireless": true}`, PostgreSQL looks up that entry and goes straight to the matching rows. Without the index, it reads and checks every row (a sequential scan).

```sql
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);
```

**What it speeds up:** the containment and existence operators `@>`, `?`, `?|` and `?&`, which work on the whole document:

```sql
SELECT name FROM products WHERE attributes @> '{"wireless": true}';   -- uses the GIN index
```

In my test on 200,000 rows, this query took **73.95 ms with a sequential scan and 1.68 ms with a Bitmap Index Scan**, about 44× faster (see Task 6).

**What it does not help:** extracting a value with `->>` and then comparing or ranging on it. The default GIN index does not support those expressions:

```sql
SELECT name FROM products WHERE attributes ->> 'color' = 'black';        -- still a Seq Scan
SELECT name FROM products WHERE (attributes ->> 'ram_gb')::int >= 16;   -- still a Seq Scan
```

For those queries, rewrite equality as `@> '{"color": "black"}'`, or create a B-tree **expression index** such as `CREATE INDEX ON products ((attributes ->> 'color'));`. A GIN index also makes writes slower and uses extra disk space, so it is worth adding only when these queries are run often.

### Q5. Where can PostgreSQL + `jsonb` replace MongoDB, and where is MongoDB better?

**PostgreSQL + `jsonb` can replace MongoDB** when the application is mostly relational but has some flexible data, such as product attributes, user settings or API payloads. You get documents and still keep:

- **Transactions:** full ACID across many rows and tables, e.g. `BEGIN; UPDATE stock …; INSERT INTO orders …; COMMIT;`. MongoDB has had multi-document transactions since version 4.0, but they cost more and are not its normal way of working.
- **Joins:** a simple `JOIN orders ON orders.product_id = products.id`. MongoDB needs `$lookup` or copies of the data inside each document.
- **Schema enforcement:** `NOT NULL`, `CHECK`, `UNIQUE` and foreign keys, even on the JSON part: `CHECK (attributes ? 'author' OR category <> 'book')`. MongoDB's `$jsonSchema` validation is optional and cannot check links between collections.

**MongoDB is better when:**

- **You need horizontal scaling.** MongoDB has built-in sharding across many servers and automatic failover with replica sets. Core PostgreSQL mainly scales vertically (a bigger machine); sharding needs an extension such as Citus.
- **Everything is a document.** For deeply nested documents that change shape often, `find`, dot notation and aggregation pipelines feel more natural than SQL with JSON operators.
- **Write volume is very high** and the records are independent (logs, events, IoT readings).

**Conclusion:** choose PostgreSQL + `jsonb` when the data has relations and needs integrity but some fields are flexible. Choose MongoDB when the data is document-shaped and must scale out across many servers.

### Task 5 — Add a new key without `ALTER TABLE`

```sql
UPDATE products
SET attributes = attributes || '{"discount_pct": 10}'

-- UPDATE 1

```

The `||` operator merges two `jsonb` objects. If the key already exists, its value is replaced. The table structure does not change, and the other 4 rows are unaffected. A new key can be removed with `attributes - 'discount_pct'`.

**Create the index:**

```sql
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);
```

**After the index (5 rows):**

```
 Seq Scan on products  (cost=0.00..1.06 rows=1 width=14) (actual time=0.008..0.008 rows=1 loops=1)
   Filter: (attributes @> '{"wireless": true}'::jsonb)
   Rows Removed by Filter: 4
 Execution Time: 0.017 ms
```

**Observation:** the planner still picks a Seq Scan. Five rows fit in a single disk page, and reading one page is cheaper than reading the index first. This is the correct choice, not a mistake.

To prove the index *can* be used, I turned off sequential scans for one query:

```sql
SET enable_seqscan = off;
EXPLAIN ANALYZE SELECT name FROM products WHERE attributes @> '{"wireless": true}';
```

```
 Bitmap Heap Scan on products  (actual time=0.015..0.016 rows=1 loops=1)
   Recheck Cond: (attributes @> '{"wireless": true}'::jsonb)
   ->  Bitmap Index Scan on idx_products_attributes  (actual time=0.010..0.010 rows=1 loops=1)
         Index Cond: (attributes @> '{"wireless": true}'::jsonb)
```

Even with sequential scans turned off, a `->>` filter cannot use this GIN index, so PostgreSQL still does a Seq Scan:

```
 Seq Scan on products  (cost=10000000000.00..10000000001.08 rows=1 width=14)
   Filter: ((attributes ->> 'color'::text) = 'black'::text)
```

**Scale test (200,000 generated rows, same query):**

| | Plan | Execution time |
|---|---|---|
| Before GIN index | Seq Scan, 199,333 rows removed by filter | **73.95 ms** |
| After GIN index | Bitmap Index Scan on `idx_products_big_attributes` | **1.68 ms** |

The index made the query about **44× faster**. The cost was a 1.7 MB index (16 kB for the 5-row table). The exact times change from run to run; the full plans are in [output/postgres_output.txt](output/postgres_output.txt).

### Task 7 — The same work in MongoDB

Script: [mongo_products.js](mongo_products.js). Run it with `mongosh --quiet mongo_products.js`.

```js
db.products.insertMany([
  { name: "Clean Code",            category: "book",      price: 499.00,    attributes: { author: "Robert C. Martin", pages: 464 } },
  { name: "MacBook Air M3",        category: "laptop",    price: 114900.00, attributes: { ram_gb: 16, cpu: "Apple M3", storage_gb: 512 } },
  { name: "Lenovo IdeaPad Slim 3", category: "laptop",    price: 52990.00,  attributes: { ram_gb: 8, cpu: "Intel Core i5-12450H", storage_gb: 512 } },
  { name: "Wireless Mouse",        category: "accessory", price: 799.00,    attributes: { color: "black", wireless: true, dpi: 1600 } },
  { name: "USB-C Hub",             category: "accessory", price: 1499.00,   attributes: { color: "grey", wireless: false, ports: 6 } }
]);
```

| Task | PostgreSQL (`jsonb`) | MongoDB | Result |
|---|---|---|---|
| Books > 300 pages | `WHERE category='book' AND (attributes->>'pages')::int > 300` | `find({ category: "book", "attributes.pages": { $gt: 300 } })` | Clean Code |
| Laptops ≥ 16 GB | `WHERE category='laptop' AND (attributes->>'ram_gb')::int >= 16` | `find({ category: "laptop", "attributes.ram_gb": { $gte: 16 } })` | MacBook Air M3 |
| Black accessories | `WHERE category='accessory' AND attributes->>'color' = 'black'` | `find({ category: "accessory", "attributes.color": "black" })` | Wireless Mouse |
| Containment | `WHERE attributes @> '{"wireless": true}'` | `find({ "attributes.wireless": true })` | Wireless Mouse |
| Key exists | `WHERE attributes ? 'author'` | `find({ "attributes.author": { $exists: true } })` | Clean Code |
| Add a key | `SET attributes = attributes \|\| '{"discount_pct": 10}'` | `updateOne({ name: "Wireless Mouse" }, { $set: { "attributes.discount_pct": 10 } })` | 1 document modified |
| Index | `CREATE INDEX … USING GIN (attributes)` covers every key at once | `createIndex({ "attributes.wireless": 1 })` covers one path | COLLSCAN → IXSCAN |

**Differences I noticed:**

1. **Syntax.** MongoDB's dot notation (`"attributes.ram_gb"`) is shorter and needs no cast, because numbers stay numbers. In PostgreSQL, I had to write `(attributes ->> 'ram_gb')::int`. If I forget the cast, the value is compared as text, so `'8' >= '16'` is true. That is an easy bug to make.
2. **Indexing.** One GIN index in PostgreSQL covers containment queries on *all* keys. MongoDB needs a separate index for each field path, or a wildcard index (`{ "attributes.$**": 1 }`). On the other hand, a MongoDB index on a path supports range queries (`$gte`), while the PostgreSQL GIN index does not, so a range query there needs an expression index.
3. **Ease of use.** For flexible-only data, MongoDB feels more natural: there is no schema to declare and documents look like JS objects. PostgreSQL needed a `CREATE TABLE`, but it gave me `NOT NULL` on `name`/`price`, a real `NUMERIC` type for money, and the option to `JOIN` this table with orders or users later.
4. **Mixing both.** In PostgreSQL, one query mixes a strict column (`category = 'laptop'`) with a flexible key. In MongoDB, every field is equally flexible: nothing stops a document from having no `price` unless I add `$jsonSchema` validation.

## Conclusion

`jsonb` lets one PostgreSQL table hold strict relational columns and schema-less attributes side by side. With the `->`, `->>`, `@>`, `?` and `||` operators and a GIN index, it handled every document-style task in this assignment that MongoDB did, and kept transactions, joins and constraints. MongoDB remains the simpler and more scalable choice when the whole data model is documents and has to be spread across many servers.
